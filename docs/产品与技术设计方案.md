# Chat with Alice 产品与技术设计方案

## 1. 文档目的

本文为 `Bot-In-The-Mirror` 的下一阶段设计基线。目标是把当前聊天原型演进为一个“对话驱动的个人执行助手”：用户可以通过文字或语音表达任务，AI 将任务拆解为可执行事项，并在本地、日历和多平台之间保持一致；后续再扩展图片识别、饮食热量和健康管理能力。

本阶段只支持单用户多设备同步，但所有核心数据都带 `userId`，服务端按租户隔离，为未来多用户、登录和权限模型保留扩展点。

## 2. 产品定位与原则

### 2.1 核心闭环

```text
表达想法 → AI 理解与拆解 → 用户确认 → 形成任务/日历 → 执行与记录 → 获得反馈与成就
```

AI 只提出结构化建议，不应未经确认修改重要数据。用户始终可以编辑、拒绝、撤销 AI 的拆解结果。

### 2.2 设计原则

- 本地优先：无网络时仍可查看、编辑和完成任务；同步在后台重试。
- 数据可解释：每条 AI 生成的任务都能追溯到原始对话、模型和提示版本。
- 隐私优先：API Key 只保存在设备安全存储；健康和图片数据默认不上传第三方。
- 小而深的模块：页面只负责展示和交互，复杂逻辑放在稳定的模块接口后面。
- 可撤销：AI 生成、批量修改、同步冲突解决都保留操作记录或可恢复状态。
- 渐进交付：先交付聊天、任务、日历、同步和正反馈，再增加图像与健康能力。

## 3. 目标信息架构

建议主导航为五个区域：

1. **对话**：聊天会话、语音输入、AI 操作卡片。
2. **任务**：收件箱、今日、项目、待确认的 AI 拆解结果。
3. **日历**：日/周/月视图，任务与日程统一展示。
4. **健康**：饮食、热量、运动和趋势；首期可先展示占位入口。
5. **我的**：模型配置、同步状态、成就、数据导出与隐私设置。

首页可保留“最近对话”和“今日重点”两个卡片，避免把聊天列表继续作为唯一工作台。

## 4. 领域模型

### 4.1 核心实体

- `User`：用户身份。当前可使用本地生成的匿名稳定 ID；未来替换为登录账号。
- `Workspace`：个人数据空间。当前一个用户一个空间，未来支持多个空间或家庭空间。
- `Conversation` / `Message`：会话和消息，消息支持文本、语音转写、图片引用和系统事件。
- `AIProviderProfile`：用户配置的兼容接口地址、模型名、参数和能力声明。API Key 引用安全存储中的密钥，不进入普通数据库。
- `Task`：可执行事项，含标题、状态、优先级、截止时间、来源、父任务和重复规则。
- `Project`：任务集合，支持目标、领域和归档。
- `CalendarEntry`：日历中的时间块，可关联一个或多个任务。
- `AIPlan`：AI 对用户意图的结构化计划，包含待确认的任务变更。
- `HealthRecord`：饮食、热量、运动等健康记录，带来源和置信度；不能替代医疗建议。
- `Achievement` / `UserAchievement`：成就定义与用户进度，记录触发事件和奖励。
- `SyncOperation`：本地待同步变更，包含操作 ID、实体版本、重试次数和同步状态。

### 4.2 状态约束

- 任务状态建议为 `inbox → planned → doing → done`，另有 `cancelled`；AI 只能生成或建议状态变更，首次创建默认进入 `inbox` 或“待确认”。
- `AIPlan` 状态为 `draft → awaitingConfirmation → applied/rejected/expired`。
- 所有可同步实体必须有：`id`、`userId`、`createdAt`、`updatedAt`、`deletedAt?`、`version`、`deviceId`。
- 删除采用墓碑记录而非立即物理删除，确保其他设备可以同步删除。

## 5. 客户端架构

建议从当前页面直接持有状态，演进为以下分层：

```text
UI 层（screens/widgets）
        ↓
用例模块（发送消息、拆解任务、完成任务、记录饮食、同步）
        ↓
领域接口（TaskRepository、ConversationRepository、AIClient、SyncEngine）
        ↓
适配器（本地数据库、Cloudflare API、用户配置的 LLM、语音/图片能力）
```

推荐目录：

```text
lib/
  core/                 # 错误、日志、时间、ID、配置
  domain/               # 实体、值对象、接口
  data/local/           # 本地数据库与迁移
  data/remote/          # Cloudflare Worker 客户端
  features/chat/        # 对话与语音输入
  features/tasks/       # 任务与项目
  features/calendar/    # 日历
  features/health/      # 健康记录
  features/achievements/# 成就
  features/settings/    # AI、同步、隐私配置
```

关键接口应保持少而深：

```dart
abstract interface class TaskRepository {
  Stream<List<Task>> watchTasks(TaskQuery query);
  Future<Task> save(Task task);
  Future<void> applyChanges(List<TaskChange> changes);
}

abstract interface class AIClient {
  Future<AIResult> complete(AIRequest request);
  Future<AIPlan> proposePlan(PlanRequest request);
}

abstract interface class SyncEngine {
  Future<SyncReport> sync({bool manual = false});
  Stream<SyncState> watchState();
}
```

页面不直接依赖 HTTP、数据库或具体模型；测试可用内存适配器替换真实实现。

## 6. 本地存储与同步

### 6.1 本地优先

使用 SQLite 系列本地数据库（Flutter 可选 Drift 或 SQLite 封装）保存聊天、任务、日历、成就和同步队列。`shared_preferences` 只保留简单偏好，不承担业务实体存储。

敏感信息分开存储：API Key、同步令牌和设备密钥使用平台安全存储；数据库中只保留 provider 配置和安全存储引用。

### 6.2 Cloudflare Worker + D1

Worker 作为唯一远程入口，负责鉴权、请求校验、限流、版本控制和 D1 读写；客户端不直连 D1。

建议远程表：

- `users`、`workspaces`、`workspace_members`：当前单用户，字段为未来成员权限预留。
- `entities`：按 `entity_type + entity_id` 存储同步实体或拆成领域表；首期可采用领域表加统一同步字段。
- `change_log`：按用户/空间记录变更游标，用于增量同步。
- `devices`：设备 ID、最后同步时间和撤销状态。

同步协议采用“推送本地变更 + 拉取游标之后变更”的双向流程：

1. 客户端本地事务写入实体和 `sync_operations`。
2. Worker 校验 `userId/workspaceId`、版本和操作幂等键。
3. 服务端接受后返回服务端版本与新的同步游标。
4. 客户端拉取游标之后的变更，应用到本地数据库。
5. 失败操作进入退避重试；冲突进入可解释的冲突记录。

冲突默认规则：不同字段优先合并；同字段以较新的 `updatedAt` 为候选，但任务完成状态、删除和日历时间变更需要生成冲突提示，不静默覆盖。未来可增加基于变更操作的 CRDT，而不是一开始引入全量复杂度。

## 7. AI 集成设计

### 7.1 用户配置

设置页支持：Provider 名称、Base URL、API Key、模型名、温度、最大输出长度、是否启用流式输出和能力标签（文本、视觉、工具调用）。提供“测试连接”和“获取模型列表”两个动作；模型列表获取失败时允许手动填写。

支持 OpenAI-compatible 协议作为第一适配器，`AIClient` 不与某一家模型绑定。API Key 不上传 Cloudflare；若未来增加服务器代理，必须单独告知用户并设计密钥托管策略。

### 7.2 任务拆解工作流

1. 用户输入文字或语音转写文本。
2. 客户端保存原始消息。
3. AI 返回严格结构化 JSON：意图、任务、时间候选、依赖、风险、需要确认的问题。
4. 客户端校验 JSON schema，非法结果不落入任务表。
5. 以 `AIPlan` 卡片展示变更预览，用户确认后一次性写入任务和日历。
6. 写入后记录模型、模型版本、提示版本和来源消息 ID。

AI 工具调用可以逐步增加：`create_task`、`update_task`、`schedule_task`、`search_tasks`。工具执行必须经过权限和参数校验；健康数据相关工具默认只读或要求明确确认。

## 8. 语音、图像与健康路线

### 8.1 语音输入

首期只做“按住说话/点击录音 → 本机或用户指定的转写能力 → 可编辑文本 → 发送”。保存音频需用户主动开启；默认只保留转写文本。要处理权限拒绝、无网络、转写失败和中途取消。

### 8.2 拍照识图与热量

后续流程：拍照/选图 → 本地压缩与脱敏预览 → 视觉模型识别食物候选及份量 → 展示不确定性和可编辑营养值 → 用户确认 → 保存 `HealthRecord`。

不把模型输出当作医疗事实；热量使用范围和置信度展示，允许用户修改。原图默认本地保存，上传视觉模型前需显式同意，并提供删除入口。

### 8.3 健康功能边界

首期只做记录、趋势和习惯反馈，不做诊断、处方或紧急判断。涉及异常值时只提示“建议咨询专业人士”，不替代医疗服务。

## 9. 成就与正反馈

成就系统基于事件而非页面按钮：`task_completed`、`plan_confirmed`、`streak_reached`、`health_logged`、`weekly_reviewed` 等事件进入成就判定模块。

反馈分三层：

- 即时：完成任务后的轻量动画、文案和经验值。
- 周期：连续天数、周回顾和趋势卡片。
- 里程碑：徽章、主题装饰或新的助手能力。

避免惩罚式设计：断签不清零历史，只显示“重新开始”；不以热量、体重或完成数量制造羞耻感。奖励规则和成就定义放在可版本化的数据中，便于将来调整而不改客户端逻辑。

## 10. 安全、隐私与多用户扩展

- 当前使用匿名 `userId + deviceId`，同步令牌可撤销；未来增加账号登录时保持数据空间 ID 不变，支持账号绑定迁移。
- Worker 必须在每个请求中校验身份、空间归属和资源所有权，不能只信任客户端传入的 `userId`。
- D1 中 API Key 只保存引用或加密密文，推荐首期完全不入库。
- 提供数据导出、删除本地数据、删除云端数据、撤销设备和清理图片/音频的入口。
- 日志禁止记录完整 API Key、原始健康图片和完整私密对话；使用请求 ID 与摘要。

## 11. 分阶段交付

### M0：基础重构

统一 `lib/services/ai_service.dart` 与模型路径，移除页面内业务状态，建立领域模型、错误模型、依赖注入和本地数据库迁移；补齐 widget/unit 测试。

### M1：本地优先任务助手

聊天持久化、任务收件箱、任务 CRUD、AI 连接测试、模型配置持久化、AI 计划预览与确认、今日任务视图。

### M2：日历与同步

日/周/月日历、任务排期、Worker API、D1 schema、设备注册、增量同步、离线队列、冲突提示和同步状态页。

### M3：语音与成就

语音输入、转写编辑、事件总线、成就规则、连续记录和周回顾。

### M4：图像与健康

拍照识图、人工确认的营养记录、健康趋势和隐私控制；完成安全评审后再扩展更多健康数据源。

## 12. 验收标准

- 飞行模式下可以查看、创建、编辑、完成任务，恢复网络后自动同步。
- 两台设备使用同一用户空间，聊天、任务、日历和成就最终一致；重复同步不会产生重复实体。
- 用户可以配置任意兼容接口并选择模型；错误响应会以可理解的方式展示，不泄露密钥。
- AI 拆解结果在用户确认前不会修改正式任务和日历。
- 语音、图片和健康数据均有权限、取消、失败、删除和隐私提示路径。
- 核心模块通过接口测试，UI 不需要启动真实 Worker 或真实 LLM 才能测试。

## 13. 尚待确认的产品决策

- 首期是否允许保存原始录音和食物原图，默认建议关闭。
- 首期采用哪一种本地数据库适配器，以及是否需要桌面端完整支持。
- 同步是否需要端到端加密；若需要，服务端将无法直接检索和生成部分内容。
- 是否引入账号登录，以及匿名数据迁移到登录账号的产品流程。
- 默认成就、经验值和健康指标的具体文案与视觉风格。
